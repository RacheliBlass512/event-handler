# Core UI Component Library & App Palette (Angular Material)

## Context

The Angular frontend is currently a fully scaffolded skeleton (standalone components, all
feature `.ts`/`.html`/`.scss` files exist as stubs) but has **zero styling** — `styles.scss`
is empty, every component `.scss` is 0 lines, and no UI library is installed. Before any
real page can be built, we need a foundation: an app-wide color palette/theme and a small
set of reusable "core" UI components (buttons, cards, badges, etc.) that every feature page
will build on.

The user shared a reference design — a UX Pilot demo at `https://fjlyut46.host.uxpilot.net/`
(React app internally, built with Tailwind + shadcn/ui + Radix). We fetched its compiled
CSS/JS directly and extracted its actual design tokens and component styling (not just a
visual impression). The user's explicit direction: **this is a design reference, not a spec
to replicate exactly** — match the overall palette and structure (colors, status semantics,
general layout feel), but the implementation should use **Angular Material** (already
decided) and prioritize clean, idiomatic Angular code over pixel-parity with the demo.

Key facts pulled from the demo (for palette/semantics reference only):
- Primary brand color: a vivid orange, HSL `24 95% 53%` ≈ `#f97316`.
- Status colors (soft-tint pills): New=blue, Assigned=amber, InProgress=orange,
  Resolved=green, Closed=gray, Canceled=red.
- Priority colors: Critical=red, High=orange, Medium/Normal=yellow, Low=green.
- Both light and dark themes are fully defined in the demo.

These map directly onto the app's real enums already in
`frontend/src/app/core/models/enums.ts` (`EventStatus`, `Priority`) — no invented values.

## Package setup

```bash
cd frontend
ng add @angular/material
# prompts: theme = Custom, typography = yes, animations = yes
ng generate @angular/material:theme-color --primary-color="#f97316" --directory=src/styles
```

This installs `@angular/material`, `@angular/cdk`, `@angular/animations` (all `^22.x`,
matching the app's existing lockstep Angular versioning) and generates a brand-accurate
tonal palette (`_theme-colors.scss`) via Material's own M3 color algorithm, rather than
approximating the orange with a built-in named palette.

Add the Material Symbols icon font via CDN link in `frontend/src/index.html` (per Angular's
standard docs approach):
```html
<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Material+Symbols+Outlined:opsz,wght,FILL,GRAD@20..48,400,0..1,0" />
```

## Theme structure

```
frontend/src/
  styles.scss                    # entry point (referenced in angular.json) — just @use's + base resets
  styles/
    _theme-colors.scss           # generated by the schematic — do not hand-edit
    _theme.scss                  # hand-written: mat.theme() call + dark-mode override hook
    _tokens.scss                 # hand-written: soft-tint tone CSS variables (light/dark via light-dark())
```

`styles/_theme.scss` — single M3 theme call, light/dark handled via CSS `color-scheme`
(Material's tokens use `light-dark()` internally, so one `mat.theme()` call covers both):
```scss
@use '@angular/material' as mat;
@use './theme-colors' as brand;

html {
  color-scheme: light dark;
  @include mat.theme((
    color: (primary: brand.$primary-palette, tertiary: brand.$tertiary-palette),
    typography: Roboto,
    density: 0,
  ));
}

.dark-theme { color-scheme: dark; }   // manual toggle hook, mirrors the demo's `.dark` class
```

`styles/_tokens.scss` — semantic tone palette, deliberately independent of Material's own
`--mat-sys-*` tokens so it never fights Material's theming:
```scss
:root {
  --tone-info-bg: light-dark(hsl(214 95% 93%), hsl(214 60% 16%));
  --tone-info-fg: light-dark(hsl(214 84% 32%), hsl(214 90% 80%));
  --tone-info-border: light-dark(hsl(214 90% 85%), hsl(214 50% 26%));
  // ...success / warning / danger / neutral, same 3-variable pattern
}
```

**Six tones, not five**: `type Tone = 'info' | 'success' | 'warning' | 'danger' | 'neutral' | 'primary'`.
Two of the demo's status colors (InProgress, High) are orange — the same hue as the brand
primary — so rather than hardcoding a duplicate orange tone, `'primary'` resolves to
Material's own `--mat-sys-primary-container` tokens (already a soft-tint of primary, and
automatically stays in sync if the brand color ever changes).

## Status/priority → tone mapping

`frontend/src/app/core/models/status-tone.ts` (pure functions, colocated near the enums but
not inside `enums.ts` itself, which is explicitly the backend-mirror file):
```ts
export function eventStatusTone(status: EventStatus): Tone { /* New→info, Assigned→warning,
  InProgress→primary, Resolved→success, Closed→neutral, Canceled→danger */ }

export function priorityTone(priority: Priority): Tone { /* Low→success, Normal→warning,
  High→primary, Critical→danger */ }
```
Exported from `core/models/index.ts`. Two thin pipe wrappers added in `shared/pipes/`
(`event-status-tone.pipe.ts`, `priority-tone.pipe.ts`) so templates read consistently with
the existing `EventStatusLabelPipe` pattern (`{{ event.status | eventStatusTone }}`).

## Component list

Everything Angular Material already provides is used **directly**, themed by the setup
above — no wrapper components: `MatButtonModule` (buttons/links), `MatCardModule`,
`MatFormFieldModule`/`MatInputModule`, `MatSelectModule`, `MatTableModule`, `MatTabsModule`,
`MatDialogModule`, `MatTooltipModule`, `MatMenuModule`. Wrapping these would just add
indirection for no benefit.

Custom components are built only where Material has no equivalent or the app needs
domain-specific composition, in `frontend/src/app/shared/ui/`:

| Component | Purpose | Key inputs |
|---|---|---|
| **Badge** | The one pill/dot implementation for status & priority labels. Not built on `MatChip` (that's for interactive/removable chip lists — overkill for a static label; the demo itself is just a styled `<span>`). | `tone = input<Tone>('neutral')`; `variant = input<'soft'\|'dot'>('soft')`; label via `<ng-content>` |
| **Avatar** | Technician/user avatar — initials only (derived from `name`), background color deterministically derived from the name (no uploaded/photo image). Material has no built-in avatar component. | `name = input<string>('')`; `size = input<'sm'\|'md'\|'lg'>('md')` |
| **StatCard** | Dashboard summary tile (icon + big number + label) — `mat-card` alone doesn't give this layout. | `icon`, `value`, `label`, `tone = input<Tone>('neutral')` |
| **EmptyState** | "Nothing here" placeholder, reused across dispatcher/technician list views. | `icon`, `title`, `message`; action via `<ng-content>` (caller drops in its own `<button mat-flat-button>`) |

All four use the Angular 22 signal `input()`/`output()` APIs and native `@if`/`@for`
control flow (no existing stub uses `@Input()` decorators, so there's no convention being
broken — this matches the repo's already signal-first idioms elsewhere, e.g.
`auth.service.ts`).

File layout:
```
frontend/src/app/shared/ui/
  tone.ts
  badge/badge.ts .html .scss .spec.ts        (class Badge, selector app-badge)
  avatar/avatar.ts .html .scss .spec.ts      (class Avatar, selector app-avatar)
  stat-card/stat-card.ts .html .scss .spec.ts
  empty-state/empty-state.ts .html .scss .spec.ts
  index.ts   # barrel export, matching core/models/index.ts convention
```

## Verification (dev-only showcase route)

Add `frontend/src/app/dev/ui-kit/` (`ui-kit.ts`/`.html`/`.scss`/`.spec.ts`), rendering every
component and variant: all six `Tone` values in both Badge variants, all three Avatar sizes
across a handful of different names (to show the per-name color variety), a row of
StatCards, an EmptyState with a projected action button, and a light/dark toggle that flips
`.dark-theme` on `<html>`.

Registered as a normal unguarded lazy route in `app.routes.ts`:
```ts
{ path: 'ui-kit', loadComponent: () => import('./dev/ui-kit/ui-kit').then((m) => m.UiKit) },
```

**To verify**: run `ng serve`, navigate to `/ui-kit`, visually confirm the orange primary
theme, all six tone pills (both soft/dot variants), initials avatars in varied per-name
colors, stat cards, and empty state render correctly, then toggle dark mode and re-check the
same set. Run `ng test` to confirm the new component spec files pass. Remove or leave the
route as a documented dev aid before final submission — user's call at that point.
